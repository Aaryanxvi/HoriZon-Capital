# Real-Money Readiness Audit — Risk Controls

**Date:** 2026-10-10
**Scope:** `backend/app/` as it runs today (LOCAL storage, MemoryBus, `EXECUTION_BROKER=ALPACA` paper).
**Method:** every finding below is reproduced by a test in `backend/tests/test_risk_controls_proof.py` that drives the real agents over a real bus against SQLite + PaperBroker/fakes (no network, no LLM, no broker calls). A `test_B*`/`test_H*` test *passing* means the defect is reproduced. Run: `cd backend && py -3.14 -m pytest tests/test_risk_controls_proof.py -q -p no:cacheprovider` → **22 passed**. Live evidence below comes from a read-only query of `~/.horizon-capital/horizon.backup-2026-10-10-prereset.db` (the ledger was `--reset` at 00:33 IST on 2026-10-10; the live `horizon.db` is now empty).

**Effective limits in the developer `.env`:** max drawdown 15 %, max position 15 %, VaR 3 %, daily loss 5 % (default), `INITIAL_CAPITAL_USD=1000000`, `SYSTEM_MODE=PAPER_TRADING`, `CIO_MODE=AI`. Code defaults differ from `CLAUDE.md` (drawdown 25 %, position 20 % in `config.py:200-201`; the doc still says 10 %/5 %).

---

## Go / No-go

**NO-GO for real money.** There is no per-position stop-loss in the live system at all (B1), the daily-loss limit *blocks* exits exactly when you need them (B2), the kill switch freezes a losing book instead of flattening it (B3), the system silently stops talking to the real broker on a 2 % NAV mismatch while still "trading" in its own simulator (B4), any agent restart doubles every order (B5), and the local ledger — not the broker — is the source of truth for positions, cash and every risk number, with no resync ever (B6: in the pre-reset ledger **$928k of the $1.01M "positions" were simulator fills**, $71k were real). Each of these alone is disqualifying. The Indian path does not exist (H7). Fix B1–B5 + H1–H6, add the tests back into CI, and re-audit before any live capital.

## Fixes (hardening wave, 2026-10-10)

Every `test_B*`/`test_H*` proof above was **inverted, not deleted**: the same test now asserts the fixed behaviour and fails on the old code. Run: `cd backend && py -3.14 -m pytest tests/test_risk_controls_proof.py -q -p no:cacheprovider` → **34 passed**; full suite **611 passed**; `ruff check app/` clean. No order was placed against any broker during this work (fakes only). Owner decisions implemented verbatim: 20 % trailing stop from the high-water mark on every long equity (`STOP_LOSS_TRAIL_PCT`, 0 disables); kill switch / halt = **stop BUYs, exits keep working, never auto-flatten**; whole shares for US equities when the broker is ALPACA so the stop can rest at the broker (`type=trailing_stop, trail_percent=20, time_in_force=gtc`, fields verified against docs.alpaca.markets — fractional qty is market/limit DAY only).

**The invariant:** a *reduce-only exit* (SELL ≤ held long qty, broker-verified on ALPACA) is never blocked by the daily-loss limit, the kill switch, a CIO HALT, the debate gate, the qty de-dup or a dead RiskAgent. It is subject only to the oversell guard and an explicit limit-price band. Every BUY keeps every gate and gains the new ones (notional cap, price band, post-trade position cap, leverage cap, broker-reachable).

### 20 % trailing stop on the validated live mix (honest PIT harness)

`backend/scripts/validate_stop_loss.py` (same data / fill model / sleeve classes as `validate_sleeve_attribution.py` + `validate_holdout_gate.py`; live mix research .500 / trend .333 / momrank .167, 20 % cap, momrank top-3). Stop model: HWM from the entry fill, ratcheted on daily highs; checked against the day's low with yesterday's HWM + today's open (no look-ahead); fills the same day at min(open, stop) − slippage (a gap through the stop fills at the open). Re-entry **A** is what the live code does (stay out until the sleeve's target rises ≥ 50 bps above the stopped weight, or goes to zero); **B** re-enters at the next rebalance (shown so the cost of A is visible). The no-stop arm reproduces the documented baselines (2008-17 Sharpe 0.71 / maxDD −19.1 vs 0.70 / −19.1).

Read plainly: the 20 % trailing stop **cuts the max drawdown materially (−18.0 → −14.4; −19.1 → −10.8) and costs return and Sharpe (0.77 → 0.64; 0.71 → 0.53)**, mostly through time out of the market after a stop (avg gross 78 % → 63 %). Re-entering at the next rebalance (B) gives most of the return back but most of the drawdown protection too. The level was not tuned; this is a measurement of the owner's choice. Caveats as for every PIT run here: quality tilt stubbed, delisted prices missing, daily bars approximate the intraday HWM/low.

### Owner decisions still open / new risks found

- **Re-entry after a stop** (rule A) was my call because a stop with the 15-min reconciler and no rule re-buys the name within 15 minutes. Rule B is a one-line change in `_reconcile`. The backtest above is the trade-off.
- **Price band on exits**: market exits are never blocked by the band (only explicit limit prices are). Blocking a stop-loss market SELL because the 30 s-old reference moved > 5 % would strand it in exactly the crash it exists for.
- **Oversell = reject, not clamp**: a SELL above held qty is rejected with the reason; stop-loss and sleeve sizing never produce one.
- **Sticky halts**: a CIO HALT or a DEAD risk-critical agent sets the same `horizon:system:halted` flag the kill switch uses; clearing is a human act (`risk reset` / RESUME).
- **Residual**: a *partially* filled trailing stop that then sits for 24 h would be swept by the 24 h stale-order cancel (its local row is OPEN/PARTIAL). Triggered stops are market orders, so this is theoretical. Holidays read as stale prices (alert only, nothing trades). The sync maps broker-only positions onto the local `BASE.EXCHANGE` convention via the known universe, else `BASE.<Alpaca exchange>` (ARCA→NYSE).

## Multi-user / service readiness (facts, not design)

- **Auth:** LOCAL mode returns a hardcoded CIO user for every request with no credentials (`dependencies.py:25-26`); `test_FACT_local_mode_bypasses_auth`. The desktop API (`api/desktop.py`) — including `POST control/halt`, `control/settings` (writes `.env`), `control/engine` and the REPL bridge that can `buy`/`sell` — is reachable by anything that can hit the port. JWT only exists on the POSTGRES path.
- **Credentials:** broker and LLM keys are plaintext in `backend/.env`, loaded by pydantic-settings (`config.py:39-43`), rewritten by `settings_panel._write_env_key` and the desktop settings endpoint. No vault, no per-user secret.
- **Isolation:** one `positions` table with `UNIQUE(symbol, exchange)` (`local_storage.py:227`), one `cash_balances` row per currency (`:111-115`), one global KV namespace (`horizon:*`), one `horizon:system:halted`. There is no account/user/tenant column anywhere. One process = one book = one set of credentials. Serving a second person means a second full process with its own `HORIZON_DATA_DIR` and `.env`.
- **Audit trail:** `orders` (with `signal_id`, `debate_id`, `rejection_reason`), `fills`, `signals`, `debate_sessions`/`debate_arguments`, `cio_advisories`/`cio_overrides`, `risk_metrics` are durable; `agent_messages` (the alert stream) is pruned after 7 days (M7). No immutable/append-only guarantee; SQLite file is writable by the process user.
- **Architecture:** single asyncio process, SQLite WAL, in-memory bus and KV. In-memory state that matters for safety and is lost on restart: `_cio_halt_active`, `_pending_signals` (debate buffer), `_last_emitted_qty`, `_processed_signal_ids`, `_sleeve_targets`, orchestrator retry counts. There is no shared-nothing boundary to put a second user behind.
